---
title: Threat model
description: Assets, attackers, trust boundaries and threats for the WebAssembly-based quickjs-rs, with status and residual risk.
---

This threat model covers the wasm-era design: QuickJS (quickjs-ng via rquickjs) compiled to `wasm32-wasip1`,
driven by wasmtime-py from a pure-Python package. It replaces the earlier model written for the PyO3 extension.
Statements are checked against the code on `main`; file references are to this repository.

## Scope

**In scope:** the Python package (`quickjs_rs/`), the guest crates (`crates/quickjs-wasm`,
`crates/quickjs-wasm-transform`), the boundary between them, snapshots, and the build and release pipeline as it
affects what ships.

**Out of scope:** the security of host functions and module loaders that applications write (covered here only as
guidance), wasmtime's internal correctness beyond noting it as a dependency, and the docs site.

**Assumptions.**

1. The Python process that embeds quickjs-rs is trusted, as is the application code that configures runtimes and
   registers host functions.
2. JavaScript and TypeScript source passed to `eval*`, returned by module loaders, or written by a language model
   may be fully attacker-controlled.
3. Values returned by host functions may contain sensitive data.
4. Snapshot bytes are trusted only if the application produced them and protected them in storage.

## Assets

| ID | Asset | Why it matters |
| --- | --- | --- |
| A1 | Host process integrity | Code execution in the Python process means full compromise of whatever it can reach. |
| A2 | Host capabilities | Files, network, databases and credentials reachable through host functions. |
| A3 | Data inside a context | Tool results, secrets and user data passed in or produced by the script. |
| A4 | Other contexts and tenants | State belonging to other users in the same process. |
| A5 | Availability | CPU, memory and event-loop time of the host. |
| A6 | Integrity of results | Applications act on values returned by evals. |

## Attackers

| ID | Attacker | Capability |
| --- | --- | --- |
| X1 | Script author | Chooses the source code: a malicious user, or a model steered by prompt injection. |
| X2 | Engine exploiter | X1 plus a working memory-safety exploit against QuickJS, so arbitrary control of guest memory. |
| X3 | Runtime exploiter | X2 plus a working exploit against wasmtime or Cranelift. |
| X4 | Snapshot tamperer | Can modify or substitute snapshot bytes at rest or in transit. |
| X5 | Supply-chain attacker | Can compromise an upstream crate, the Rust toolchain, wasmtime-py or the release path. |

## Trust boundaries

| ID | Boundary | Enforced by |
| --- | --- | --- |
| TB1 | Guest linear memory ↔ host process | WebAssembly memory isolation (wasmtime); bounds-checked host reads (`_Instance.read`). |
| TB2 | Script ↔ host functions | Name lookup in a per-instance table; argument marshalling; error sanitization (`_Instance._host_call`, `hostfn.rs`). |
| TB3 | Script ↔ module loader | Host `normalize` / `load` callbacks; name and source length caps (`modules.rs`). |
| TB4 | Context ↔ context | Separate instance and store per context; handle owner checks (`handle.py`). |
| TB5 | Snapshot bytes ↔ live context | Header validation only: magic, format, `build_id`, sizes (`_Instance.restore`). |
| TB6 | Source ↔ transform guest | Separate wasm instance per context for OXC (`_transform.py`). |
| TB7 | Upstream code ↔ shipped wheel | Pinned lockfiles, wasm built from source in CI, RustSec scan, git-source policy. |

## Threats

Status values: **Mitigated** (the library prevents it), **Partial** (the library limits it; residual risk
remains), **Accepted** (by design; the application must handle it).

### Sandbox escape

**T1: Engine memory corruption reaches the host.** *X2, TB1, A1.* A QuickJS bug gives the attacker arbitrary
reads and writes in guest memory.
*Mitigation:* the guest can't address host memory. The host bounds-checks every `(ptr, len)` it reads, caps
lengths, never dereferences a guest pointer on its side, and looks up host-call names in a dictionary (an unknown
name is an error). Handles are only meaningful inside the guest. Every export is wrapped in `catch_unwind`, so a
Rust panic becomes a status code.
*Residual:* the attacker controls everything the context computes, including values returned to Python, so
results of an eval over attacker code must be treated as untrusted (A6). **Status: Mitigated** for A1.

**T2: wasmtime or Cranelift bug crosses the boundary.** *X3, TB1, A1.* The guest runs in-process, compiled by
Cranelift.
*Mitigation:* none inside quickjs-rs beyond depending on `wasmtime>=45`.
*Residual:* this is the design's residual escape path. Keep wasmtime updated; add process or container isolation
for workloads that must assume X3. **Status: Accepted.**

### Host capabilities

**T3: Script abuses a host function.** *X1, TB2, A2.* Any registered function is callable by any code in the
context, with any arguments, any number of times.
*Mitigation:* only names explicitly registered on that context are callable; arguments arrive as plain Python
values (functions, symbols and promises can't be passed).
*Residual:* everything a host function can do, the script can do. This is the main risk in programmatic tool
calling. Applications must validate arguments, enforce the end user's permissions, and budget calls (see the
[security model](/security#running-untrusted-code)). **Status: Accepted.**

**T4: Host internals leak into the script through errors.** *X1, TB2, A3.* Exception messages often contain paths,
queries or secrets.
*Mitigation:* the failure path returns a sentinel and the guest creates `HostError: Host function failed`; no host
string is written into JS. Async rejections use the same fixed name and message. The original exception is raised
only to the Python caller.
*Residual:* values host functions *return* are visible, and the re-raised exception reaches application logs.
**Status: Mitigated** for the JS side.

**T5: Script steers the module loader.** *X1, TB3, A2.* `normalize(base, specifier)` receives attacker-chosen
specifiers, including `../` paths.
*Mitigation:* no built-in loader; nothing loads unless the application installs one. Names over 4096 bytes and
sources over 16 MiB are rejected. Returning `None` refuses.
*Residual:* a loader backed by a file system or network must apply its own allowlist. Loader callbacks run
synchronously and can't be interrupted while they run. **Status: Accepted.**

### Resource exhaustion

**T6: CPU exhaustion.** *X1, A5.* Infinite loops, microtask storms, pathological regexes.
*Mitigation:* the per-eval wall-clock deadline is polled by QuickJS's interrupt handler, including during microtask
drains, and the interrupt is uncatchable. `execute_pending_jobs` runs at most 100,000 jobs
per call. The context survives a timeout.
*Residual:* time inside host functions and loader callbacks can't be interrupted; awaited async host time doesn't
count toward the deadline, so a script can keep a run alive indefinitely by awaiting slow tools; there's no CPU-time
(as opposed to wall-clock) budget. Bound runs with `asyncio.timeout`. **Status: Partial.**

**T7: Memory exhaustion.** *X1, A5.* Large strings, arrays, deep structures.
*Mitigation:* `memory_limit` (64 MiB by default) is enforced by QuickJS over its allocations. Since #58 the guest
uses an allocator that reports real block sizes, so the limit is accurate. Exceeding it raises a catchable JS error
and the context survives. Marshalling is capped at depth 128 and guest inputs at 64 MiB.
*Residual:* on quickjs-rs 0.2.6 and earlier, each allocation counted as about 8 bytes, so a script could hold
several times the limit. No wasmtime memory limit is set on the store: allocations outside QuickJS (marshalling
buffers, the deferred registry) aren't counted, linear memory only ever grows, and `memory_limit=None` removes the
bound entirely. Each context costs about 1.3 MB before any script runs. **Status: Partial.**

**T8: Stack exhaustion.** *X1, A5.* Deep recursion.
*Mitigation:* the wasm shadow stack is finite, so recursion ends in a wasmtime trap rather than host stack
overflow.
*Residual:* QuickJS's stack check is compiled out for WASI, so `stack_limit` has no effect and the failure is a
`wasmtime.Trap`, not a `QuickJSError`; callers catching only `QuickJSError` miss it, and the context's state after a
trap isn't guaranteed. **Status: Partial.**

**T9: Host-call fan-out.** *X1, A2, A5.* One `Promise.all` can start thousands of async host calls; a loop can make
millions of sync calls within the timeout.
*Mitigation:* none in the library: each async call becomes an asyncio task.
*Residual:* applications must cap concurrency and call counts inside their host functions. **Status: Accepted.**

### Isolation between users

**T10: Cross-context data leakage.** *X1, TB4, A3, A4.* A script reads another context's data.
*Mitigation:* every context is a separate wasm instance and store; there is no shared heap and no API to reach
another context. Handles from one context are rejected in another. Concurrent creation and use of contexts across
threads is covered by tests (`tests/test_isolation.py`).
*Residual:* contexts on one `Runtime` share its module loader callbacks, clock, limits and deadline slot; anything
those callbacks close over is visible to all of them. **Status: Mitigated** for memory; use one `Runtime` per
tenant for the rest.

**T11: State persistence across runs.** *X1, A3, A6.* A context reused for a second user keeps globals, modified
prototypes (`Array.prototype.map = ...`), cached modules and data from the first.
*Mitigation:* none; persistence is intended behavior.
*Residual:* create a fresh context, or restore a known snapshot, per untrusted run. **Status: Accepted.**

**T12: Deadline interference across threads.** *A5.* Contexts on one `Runtime` share one deadline slot. Evals from
different threads on contexts of the same runtime can clear or replace each other's deadline, leaving a script with
no timeout.
*Mitigation:* documented rule: one thread per context and one runtime per thread; `ThreadWorker` makes this easy.
**Status: Accepted.**

### Snapshots

**T13: Snapshot tampering or forgery.** *X4, TB5, A1, A6.* A modified image is restored.
*Mitigation:* restore checks the magic, format version, `build_id` (SHA-256 of the guest wasm), image length and
stack pointer, in that order, before writing anything.
*Residual:* there is no signature or MAC. A crafted image with the right header is arbitrary guest state: the
attacker controls every value the context will return, its limits (the QuickJS memory limit is part of the image)
and which host functions its code calls with which arguments. It stays inside the sandbox (T1), but A2 and A6 are
exposed. The header's declared size also decides how far linear memory grows on restore, up to the wasm32 maximum
of 4 GiB. Applications must sign or MAC snapshots, store them under access control, and check the size before
restoring. **Status: Accepted.**

**T14: Snapshot disclosure.** *A3.* A snapshot contains the whole heap: every string, every tool result, anything
that was ever in memory and not yet overwritten.
*Mitigation:* none in the library.
*Residual:* treat snapshots like the most sensitive data that passed through the context; encrypt at rest if
needed; don't share a snapshot across users. **Status: Accepted.**

### Other channels

**T15: Timing and clock side channels.** *X1, A3.* By default scripts read real time through `Date.now()` and
`performance.now()`, which helps time host operations.
*Mitigation:* a `clock` callback replaces every WASI clock the guest reads.
*Residual:* a script can still measure time by counting loop iterations around a host call. `Math.random()` is not cryptographic. **Status: Partial.**

**T16: Transform parser bugs.** *X1, TB6.* TypeScript is parsed by OXC before QuickJS sees it.
*Mitigation:* OXC runs in its own wasm instance per context; failures recreate the instance and surface as a
module-load error or `SyntaxError`. **Status: Mitigated.**

**T17: Guest output to host stdio.** *A5.* The guest's WASI stdout and stderr are the host's.
*Mitigation:* JS has no API that writes to them. Only engine-level messages (for example a Rust panic message) can
appear. **Status: Mitigated.**

### Supply chain

**T18: Compromised upstream or build.** *X5, TB7, A1.* rquickjs and quickjs-ng (C), OXC, the Rust toolchain,
wasmtime-py, and PyPI publishing.
*Mitigation:* the guest wasm is built from source in CI and never committed; Cargo lockfiles pin versions; the
`dependency-security` workflow runs `cargo audit --deny warnings` and a policy check on git sources for the QuickJS
guest's lockfile; actions are pinned by commit SHA. Upstream C code compiled into the guest is contained by the
sandbox (T1).
*Residual:* the RustSec scan covers `crates/quickjs-wasm/Cargo.lock` only, not the transform crate; wasmtime-py is a
range dependency (`>=45`), so installs pick up new releases. **Status: Partial.**

## Investigated and dismissed

- **Deferred id confusion.** Settling uses a `u32` id. The guest removes an entry when it settles it and returns
  `STATUS_BAD_INPUT` for unknown ids, so a stale or forged id can't settle another call. Ids wrap after 2³² calls in
  one context; a collision would need a deferred to stay pending across four billion others.
- **Cross-context handles.** Handles carry their owning context and every operation checks it, so a handle can't be
  used to reach another instance. Even if the check were bypassed, a handle is a pointer into one guest's memory and
  means nothing elsewhere.
- **Host-call routing across threads.** Imports are registered once on a shared linker and routed by a thread-local
  naming the instance currently executing on that thread, so a host call can't be delivered to another thread's
  instance. `tests/test_isolation.py` exercises this concurrently.
- **Stack pointer in snapshots.** The restored stack pointer is checked to lie within the image.
