quickjs-rs is built to run code that a language model wrote and nobody reviewed.
This page describes what that buys you and what it does not.

<Callout type="warning" title="Not yet audited">
  quickjs-rs has not had an independent security audit. If you find a way out of the sandbox, do not open a public
  issue. Report it privately through the repository's [security page](https://github.com/langchain-ai/quickjs-rs/security).
</Callout>

## Where the boundary is

The boundary is WebAssembly. The JavaScript engine is compiled to a wasm module, and every `Context` is a separate
instance of it with its own linear memory. Code inside an instance can read and write that memory and nothing else.
It cannot address Python objects, other contexts, or the rest of your process.

Everything else follows from that:

- **No ambient authority.** The instance gets no files, no environment variables, and no network. The JavaScript
  globals have no `console`, `fetch`, timers, `require`, or `process`.
- **The only way out is a short list of imports.** The guest can call the host to run a host function, to ask
  whether its deadline has passed, and to resolve and load a module. Each of those does only what you configured.
- **An engine bug stays inside one context.** A memory-safety bug in QuickJS lets an attacker control that context's
  memory. That memory holds nothing of yours that you did not put there.

```python
from quickjs_rs import Runtime

ambient = ["console", "fetch", "setTimeout", "require", "process", "WebAssembly"]

with Runtime() as rt, rt.new_context() as ctx:
    found = ctx.eval(f"{ambient}.filter((name) => name in globalThis)")
    print(found)
    #> []
```

The remaining escape path is wasmtime itself. wasmtime compiles and runs the guest inside your process, so a bug in
wasmtime or its Cranelift compiler could cross the boundary. Keep `wasmtime` up to date. If you must assume an
attacker who can exploit wasmtime, also run quickjs-rs in a container or a separate process.

## Host functions are capabilities

The sandbox guarantees that a script reaches nothing you did not hand it. It cannot guarantee that what you handed
it is safe.

Every function you register can be called by any code in the context, with any arguments, as many times as it likes.
A host function that takes a path and reads it is a file-system primitive that you wrote. Validate arguments the way
you would validate an HTTP request body, and apply the permissions of the end user, not of the agent.

When a host function raises, the script sees a fixed error with no detail. Exception messages often contain paths,
queries, or secrets, and anything a script can read can end up in model output. The original exception stays in
Python:

```python
from quickjs_rs import Runtime

with Runtime() as rt, rt.new_context() as ctx:

    @ctx.function
    def read_config() -> str:
        raise RuntimeError("cannot connect: password=hunter2")

    print(ctx.eval("try { read_config() } catch (e) { `${e.name}: ${e.message}` }"))
    #> HostError: Host function failed

    try:
        ctx.eval("read_config()")
    except RuntimeError as e:
        print("Python sees:", e)
        #> Python sees: cannot connect: password=hunter2
```

The values a host function returns are another matter. The script can read all of them.

## Contexts do not share memory

Two contexts never share JavaScript objects, even when one `Runtime` made both.

```python
from quickjs_rs import Runtime

with Runtime() as rt, rt.new_context() as a, rt.new_context() as b:
    a.eval("globalThis.secret = 42")
    print(b.eval("typeof secret"))
    #> undefined
```

A context does keep its own state from one eval to the next. Globals, modified prototypes, and cached modules are all
still there for the next script. Do not reuse a context across users.

A runtime's contexts do share some things: the module loader, the clock, and the timeout slot. Use one `Runtime` per
tenant, and one per thread.

## Limits have edges

Memory and time limits stop most runaway scripts. Each has gaps you should know about before relying on it:

| Limit | Default | What it does not cover |
| --- | --- | --- |
| `memory_limit` | 64 MiB per context | Memory outside the QuickJS heap. Before 0.3.0 it also undercounted badly. |
| `timeout` | 5 seconds per eval | Time spent awaiting async host functions, and time inside a blocking sync host function. |
| Stack | Fixed by the wasm build | Deep recursion raises `wasmtime.Trap`, which is not a `QuickJSError`. |
| Async host calls | No limit | One `Promise.all` can start thousands of calls. |

[Resource limits](/concepts/resource-limits) covers each one.

## Snapshots are trusted input

A [snapshot](/concepts/snapshots) is a raw copy of a context's memory. Restoring one checks that it came from the same
build of the engine, but snapshots are not signed. Anyone who can change the bytes controls everything the restored
context computes and returns. A snapshot also holds every secret the context ever saw.

Only restore snapshots you created, from storage only you can write.

## Error classes are not proof

quickjs-rs picks the exception class from the error's `name` and `message`. A script can throw an object that looks
like an out-of-memory error:

```python
from quickjs_rs import MemoryLimitError, Runtime

with Runtime() as rt, rt.new_context() as ctx:
    try:
        ctx.eval("throw { name: 'InternalError', message: 'out of memory' }")
    except MemoryLimitError:
        print("raised as MemoryLimitError")
        #> raised as MemoryLimitError
```

Use exception classes to decide how to report a failure, not to decide what the script was allowed to do.

## Checklist for untrusted code

<Steps>
  <Step title="Register the fewest tools you can">
    Register only what the task needs. Never register a general-purpose function: a Python `eval`, a shell, raw file
    or HTTP access, or a function that calls "any tool by name".
  </Step>
  <Step title="Validate inside every tool">
    Check types and ranges, resolve paths and URLs against an allowlist, and enforce the end user's permissions.
    Assume the script's author sees everything you return.
  </Step>
  <Step title="Budget the run">
    Keep `memory_limit` set and pick a `timeout` that fits the task. Wrap `eval_async` in `asyncio.timeout()` to bound
    total time, because awaited host calls do not count against `timeout`. Cap how often, and how many at once, each
    tool can run.
  </Step>
  <Step title="Start from clean state">
    Run each untrusted program in a new context, or in one restored from a snapshot you made.
  </Step>
  <Step title="Separate tenants">
    Use one `Runtime` per tenant. For hostile multi-tenant workloads, add process or container isolation and recycle
    workers after a timeout, an out-of-memory error, or a trap.
  </Step>
  <Step title="Catch every failure">
    Catch `QuickJSError` and `wasmtime.Trap`. Close the context after a trap.
  </Step>
</Steps>
